# eSchool Management System — Architecture

> Status: Approved plan (Phase 0). Keep this file in sync whenever a structural decision changes.

## 1. Goals and principles

| Principle | What it means in practice |
|---|---|
| One web panel, one Android app | No separate apps per role. Login returns the user's roles, permissions and scopes; menus, screens and actions are generated from them. |
| One source of truth | A single NestJS API + PostgreSQL. Web and app read the same endpoints, so records, amounts and statuses are always identical. |
| Scope everywhere | Every query is filtered by school / branch / session / section / own children before it runs. |
| Nothing is lost | Archive instead of delete; corrections and reversals create new records with reason + actor; full audit trail. |
| Background, not blocking | Heavy work (PDFs, bulk notifications, imports, exports, payroll, backups) runs in job workers. Android UI thread only renders. |
| Build each module once | A module is finished end-to-end (DB → API → web → app → tests → docs) before it is marked done. |
| Shared components | Web and Android each have one design system package; feature code only composes shared components. |
| Small files | One responsibility per file; logic in services/hooks/ViewModels, not in controllers, JSX or composables. |

Out of scope: selling, subscriptions, billing of schools.

## 2. Hierarchy

```
School ─┬─ Branch ─┬─ Academic Session ─┬─ Class ─┬─ Section ─┬─ Enrollment ── Student
        │          │                    │         │           └─ Subject assignments (teacher)
        │          │                    │         └─ Subjects
        │          │                    └─ Terms, holidays, deadlines
        │          └─ Staff assignments, rooms, timings, working days, settings
        └─ Branding, policies
```
Example: Bright School › Main Branch › 2026-27 › Class 5 › Section A.

- A student belongs to the school; their **enrollment** links them to a section in a session (history kept across sessions/branches).
- A parent (guardian) links to many students, possibly in different branches.
- A teacher can teach many sections/subjects, possibly in more than one branch.

## 4. Tech stack

| Layer | Choice |
|---|---|
| API | NestJS 11 (TypeScript), class-validator DTOs, Swagger/OpenAPI |
| ORM / DB | Prisma (multi-file schema) on PostgreSQL 16 |
| Jobs | BullMQ on Redis (queues: `notifications`, `documents`, `reports`, `imports`, `payroll`, `maintenance`) |
| Files | S3-compatible storage (MinIO locally), pre-signed upload/download URLs |
| Push | Firebase Cloud Messaging; email (SMTP) and SMS behind adapter interfaces |
| Payments | `PaymentGateway` adapter interface; `ManualGateway` now, JazzCash/Easypaisa/bank later |
| Web | Next.js, TanStack Query, react-hook-form + zod, Tailwind CSS, Radix primitives, lucide icons |
| Android | Kotlin, Compose + Material3, Hilt, Navigation Compose (type-safe), Retrofit + OkHttp + kotlinx.serialization, Room, DataStore, WorkManager, Coil |
| Contract | OpenAPI JSON generated by the API → `openapi-typescript` types for web; Kotlin DTOs mirror the spec |

## 5. Backend architecture (SchoolApi)

```
src/
├─ main.ts, app.module.ts
├─ config/                     typed env config (zod validated)
├─ core/
│  ├─ prisma/                  PrismaService, transaction helper
│  ├─ auth/                    login, refresh rotation, password reset, sessions, guards
│  ├─ rbac/                    permission catalog, @RequirePermission, ScopeService, PolicyGuard
│  ├─ audit/                   AuditService + interceptor (who/what/when/before/after)
│  ├─ approvals/               generic approval engine (requests, steps, handlers registry)
│  ├─ notifications/           in-app + push/email/SMS channels, delivery log, retries
│  ├─ files/                   upload policy, scanning hook, signed URLs
│  ├─ jobs/                    BullMQ module, queue names, base processor
│  └─ common/                  pagination, error filter, response envelope, decorators
└─ modules/
   ├─ schools/  branches/  users/  roles/  sessions/  academics/ (classes, sections, subjects, rooms)
   ├─ admissions/  students/  guardians/  documents/  staff/
   ├─ timetable/  syllabus/  attendance/  leave/  diary/
   ├─ activities/  notices/  messaging/  complaints/  meetings/  health/  pickup/
   ├─ exams/  results/  promotion/  certificates/
   ├─ fees/  payments/  payroll/  expenses/  inventory/
   ├─ reports/  settings/  backups/  imports/
```

Each domain module follows the same shape:
```
<module>/
├─ <module>.module.ts
├─ <module>.controller.ts      routes only; decorators for permission + scope
├─ <module>.service.ts         business rules, state transitions
├─ <module>.repository.ts      Prisma queries, always takes a resolved Scope
├─ dto/                        request/response DTOs
├─ <module>.events.ts          domain events (e.g. AttendanceSubmitted)
└─ jobs/                       processors for this module's background work
```

Request pipeline:
`JwtAuthGuard → ActiveAccountCheck → PolicyGuard(permission + scope) → ValidationPipe → Controller → Service (transaction) → AuditInterceptor → Response envelope`

Domain events (NestJS EventEmitter) decouple side effects: a service commits its transaction, then emits an event; listeners enqueue jobs (notify parents, generate PDF, update dashboards). Nothing slow runs inside the request.

### Response conventions
- Success: `{ data, meta? }`; lists use cursor or page pagination `{ data: [], meta: { page, pageSize, total } }`.
- Error: `{ error: { code, message, details? } }` with stable `code` values (`FORBIDDEN_SCOPE`, `RECORD_LOCKED`, `APPROVAL_REQUIRED`, `VALIDATION_FAILED`, ...).
- Money in API is integer minor units (`amountMinor`) plus `currency`.
- Dates: ISO-8601; school-local dates as `YYYY-MM-DD`, timestamps in UTC.

## 6. Roles, permissions and scope

### 6.1 Roles
| Role | Portal | Summary |
|---|---|---|
| SUPER_ADMIN | Web (full), App (dashboard + approvals) | Whole system; creates schools, branches, principals |
| PRINCIPAL | Web + App | Assigned branches only, within granted authority |
| COORDINATOR | Web + App | Section group / class range in a branch; reviews teachers, can act as teacher |
| HEAD_TEACHER | Web + App | Like coordinator for a department/wing |
| TEACHER | Web + App | Assigned sections/subjects only |
| HELPER | App (+ web) | Drafts for assigned sections; no approvals, fees, salary |
| ACCOUNTANT | Web (+ app) | Finance work within branch and amount limits |
| PARENT | App + Web | Verified children only, with child switcher |

Roles are data, not code: a role is a named bundle of permissions. Custom roles can be created from the Roles & Permissions screen.

### 6.2 Permission = action on module
Format `module.action`, e.g. `attendance.submit`, `fees.concession.approve`, `exams.publish`. Actions: `view, add, edit, submit, approve, publish, export, delete(archive)`.

### 6.3 Scope
A **role assignment** = `user + role + scopeType + scopeId + validFrom/validUntil`.

| scopeType | Meaning |
|---|---|
| GLOBAL | Super admin |
| SCHOOL | All branches of one school |
| BRANCH | One branch |
| SECTION | One section (class teacher, helper) |
| SUBJECT_SECTION | One subject in one section (subject teacher) |
| SELF | Own staff record (salary, leave) |
| GUARDIAN | Own verified children |

`ScopeService.resolve(user, permission)` returns the set of branch/section/student IDs the user may touch; repositories always apply it. Temporary assignments (substitutes) expire automatically via `validUntil`.

### 6.4 Special working modes
- **Supervisor proxy ("act as teacher")** — Principal, Coordinator and Head Teacher hold `teacherwork.proxy` for their scope. They can mark attendance, write diary, enter marks, update syllabus progress for any section in scope. Records store `performedById` and `onBehalfOfStaffId`. This supports schools where teachers are not allowed phones.
- **Probation (new teacher)** — `StaffProfile.requiresReview = true` + `reviewerId`. Their submissions create an approval request (`PROBATION_REVIEW`) instead of publishing; on approval the original action completes. Principal removes the flag when the teacher is ready.
- **Helper drafts** — helper output is always `DRAFT` until the responsible teacher finalizes.
- **Multiple roles** — one login may hold several assignments (e.g. teacher + parent). The client shows a context switcher; the active context is sent as header `X-Active-Role`.

### 6.5 Menu catalogue
The API exposes `GET /me` → `{ user, assignments[], permissions[], activeContext, children[] }`. Both clients hold a static **navigation catalogue** (id, label, icon, route, required permission). The menu is the catalogue filtered by permissions. Base menus per the brief: Super Admin 20, Principal 16, Teacher 12, Parent 10; added modules (admissions, health, pickup, complaints, meetings, expenses, inventory, certificates) appear under the relevant section group for roles that hold their permission.

## 7. Approval engine (shared)

One mechanism for every "needs a decision" item.

```
ApprovalRequest { id, type, entityType, entityId, branchId, requestedById,
                  status: PENDING | APPROVED | REJECTED | RETURNED | CANCELLED,
                  currentStep, payload(json snapshot), reason, createdAt }
ApprovalStep    { requestId, order, approverRole | approverUserId, amountLimitMinor?, decision, comment, decidedAt }
```
- Each module registers a handler: `onApproved(request)` / `onRejected(request)`.
- Routing rules come from branch settings (e.g. concessions above limit → Super Admin).
- Self-approval is blocked (a principal's own salary goes to a higher admin).
- One inbox on web and app: "Approvals" filtered by what the user can decide.

Types: `HELPER_DRAFT, PROBATION_REVIEW, ATTENDANCE_CORRECTION, LEAVE, TIMETABLE_PUBLISH, SYLLABUS_PLAN, ACTIVITY, DIARY_MODERATION, RESULT_PUBLISH, PROMOTION, CONCESSION, REFUND, PAYMENT_REVERSAL, PAYROLL, EXPENSE, PURCHASE_ORDER, ADMISSION, CHILD_LINK, CONTACT_CHANGE, EARLY_LEAVE, CERTIFICATE`.

## 8. Web architecture (SchoolWeb)

```
src/
├─ app/
│  ├─ (auth)/login/page.tsx
│  ├─ (portal)/layout.tsx           sidebar + topbar from /me
│  └─ (portal)/<module>/...         thin route files that render feature pages
├─ components/
│  ├─ ui/                           primitives: Button, Input, Select, Card, Badge, Tabs, Dialog, Table...
│  └─ shared/                       DataTable, FilterBar, PageHeader, FormField, FormDialog, StatusBadge,
│                                   ApprovalActions, AuditTimeline, FileUploader, ChildSwitcher,
│                                   ScopePicker, MoneyText, EmptyState, ConfirmDialog, StatCard
├─ features/<module>/
│  ├─ api.ts                        TanStack Query hooks (queries + mutations)
│  ├─ schemas.ts                    zod schemas for forms
│  ├─ types.ts
│  └─ components/                   module-specific pieces built from shared components
├─ lib/                             http client, auth session, permissions, formatters
└─ config/navigation.ts             navigation catalogue
```
- Auth: access token in memory, refresh token in httpOnly cookie via Next route handler (see security.md).
- Data: TanStack Query for caching, background refetch and optimistic updates; no data fetching in components beyond hooks.
- Heavy exports: request → job id → poll → signed download link.

## 9. Android architecture (SchoolApp)

```
:app                    MainActivity, AppNavHost, RoleShell, Application (Hilt, WorkManager config)
:core:common            AppResult, DispatcherProvider, Clock, extensions
:core:model             domain models shared by features
:core:network           Retrofit service interfaces, DTOs, AuthInterceptor, TokenAuthenticator
:core:datastore         SessionStore (tokens, active role) — encrypted
:core:database          Room DB, DAOs, entities, OutboxEntity (offline queue)
:core:data              repositories (interfaces + implementations), mappers
:core:designsystem      theme (tokens), shared composables
:core:sync              SyncWorker, OutboxProcessor, scheduling
:core:navigation        NavigationCatalog, route definitions, permission filter
:feature:<name>         screen + ViewModel + UiState per feature
```

Feature module shape:
```
feature/attendance/
├─ AttendanceRoute.kt        collects state, wires callbacks (no logic)
├─ AttendanceScreen.kt       stateless UI from shared components
├─ AttendanceViewModel.kt    StateFlow<AttendanceUiState>, intents
├─ AttendanceUiState.kt
└─ components/               small feature-only composables
```

Threading model:
- ViewModel launches in `viewModelScope`; repositories switch to `DispatcherProvider.io`.
- Room and Retrofit are suspend/Flow; no blocking calls.
- Uploads, sync, and periodic refresh run in WorkManager (constraints: network connected).
- StrictMode on in debug builds to catch main-thread disk/network.
- Composables never call repositories; they receive state and emit events.

Offline (attendance + diary):
- Drafts saved to Room immediately; an `OutboxEntity` records the pending API call with an idempotency key.
- `SyncWorker` sends outbox items in order; server returns canonical record; conflicts (record already locked/submitted by someone else) show a "needs attention" state.
- Server is the source of truth; cached lists refresh on resume.
